# Game retrospective integration research

Research supports adding the retrospective to the existing engine execution and moving its final boundary after the last accepted statement. A separate worker or completion queue is unnecessary. The principal work is changing what currently treats the first authoritative outcome as the end of execution.

This is read-only source research in `/Users/user/Development/influence-game`, on `codex/production-studio`, on 2026-10-10. That checkout contains ongoing Studio edits. No application code, databases, providers, deployed services, or existing Studio changes were modified or exercised for this research. The conclusions below are source findings and implementation recommendations, not runtime verification.

## Final-boundary recommendation

Use three distinct facts:

1. **Outcome determined:** an existing game-owned canonical outcome fixes the winner/faction/draw. The replay can show results, and an explicit results read can return them.
2. **Retrospective in progress:** the same owned run continues one contestant at a time. The catalog remains `in_progress`, so normal ownership, journaling, adoption, and delivery remain applicable. A failure may suspend execution while preserving the outcome.
3. **Execution finished:** the retrospective completion record permits terminal settlement, `completed`, owner closure, transcript sealing, final cost capture, and completion-triggered downstream work.

This refines the earlier high-level proposal to mark the catalog completed before the epilogue. Keeping the existing operational status until the new final boundary avoids extending every owner and provider fence to completed games. Canonical outcome availability must therefore become independent of catalog completion. Completion-dependent ratings, rewards, learning entitlements, and media jobs stay at the final boundary; their publication is later, while the competitive result is already immutable.

## Data and context decisions

Canonical start, accepted-statement, and retrospective-completion records belong to each game's existing canonical history. They establish order, actor, original outcome boundary, and exactly-once local acceptance. No separate statement queue or duplicate authoritative speech table is needed.

A bounded private dossier must be frozen before the first call and reused after restart. Recommended storage is one immutable game-scoped input row, containing its original outcome source, digest, schema/prompt version, complete chronological summary and coverage. Existing logs remain the authority for statements and their order; this private row supplies request content, not another mutable execution counter. Use existing execution/turn records for progress and planned slots. Confirm the final SQL shape against the closed validators during the contract task before adding a migration.

The dossier must include every played phase's consequential facts, no-action/tie resolutions, complete final outcomes, and a permitted dialogue representation. It is not equivalent to the current results recap or a highlight collection: those cannot explain the complete social story. The shared layer checks coverage and size; explicit adapters supply Influence and Werewolf facts. Other contestants' private thinking, native reasoning, owner strategies, and raw prompts are excluded. Own frozen character/strategy is supplied only to its speaker.

Use original source order for Influence exits, nonwinning finalists next, winner last. Werewolf partitions deaths and survivors, orders deaths by canonical resolution, shuffles survivors with a dedicated seeded purpose, and persists the resulting complete order. No gameplay random stream is advanced by this shuffle. Previous accepted statements are verbatim, in order; adopting this same behavior for Werewolf remains the documented proposed default.

An accepted provider response can be replayed without redispatch. A crash after remote dispatch but before durable acceptance may still duplicate provider billing; do not promise exactly-once remote inference. The established [provider-journal learning](../solutions/architecture-patterns/coordinate-provider-attempts-with-durable-fallback-authority.md) applies directly.

## Boundaries to keep small

- Use existing Influence sequence links and Werewolf audience/cursor links. Canonical epilogue entries give stable anchors; a new route namespace or independent global replay clock is unnecessary.
- Reuse speech labels and recipe policies, existing portrait/solo visuals, speech timing, music transport, recordings, and the sampled export composition. A new ProductionMoment kind or new generated artwork is not needed for the initial feature.
- Reuse the current provider manifest and budget policy; record a distinct retrospective action for accounting. Final capture includes the entire run, so costs must not be prematurely sealed at the outcome.
- Add bounded MCP retrospective inspection. A producer recovery command, if provided, wraps the same guarded runtime resume used by admin. Current MCP producer tools are largely diagnostic; mutation authorization must be defined and tested rather than inferred from read access.
- Historical generation was not requested. Do not add a backfill worker, a second start workflow, or an automatic read-time generation path to the first delivery. Existing absence is explicit; do not synthesize old statements or infer missing facts from transcript prose.
- Retrospective failure keeps its accepted prefix and freezes the next slot. Suspend/recover that same run; later speeches cannot be generated before an unavailable predecessor is repaired. Result readers must still show an already established outcome and avoid the current generic “No winner” interpretation of a paused run.

## Remaining implementation decisions

The execution contract task must finalize event names, phase/cursor shape, the private dossier SQL shape, output character/context limits, and whether any persisted contract version must change. These are bounded implementation decisions, not reasons for another worker or a compatibility adapter. Record them before engine implementation begins.

Keep ordinary completion side effects at the new final boundary. Consequently, a stalled retrospective delays rewards/ratings/learning credits and full export readiness even though viewers can see the outcome. This tradeoff is explicit in the implementation plan; avoiding it would require a larger split-settlement design. No split settlement is planned.

The implementation tasks and proof boundaries are in the [task plan](../plans/2026-10-10-004-feat-game-retrospectives-implementation-plan.md). No tests or live trials were run for this documentation-only research stage.
