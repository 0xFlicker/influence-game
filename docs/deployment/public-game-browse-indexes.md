# Public game browse indexes

The public games page uses direct keyset queries. The ordinary migration creates the two immutable lookup functions only; its transaction must not build indexes on `games`, because that could hold a write-blocking lock throughout the migration transaction.

The five browse indexes are built one at a time with an explicitly supplied `DATABASE_URL`. The API image bundles the migrator as `dist/migrate.js` and the builder/checker as `dist/public-browse-indexes.js`. With the candidate image and its normal migration directory, `bun dist/migrate.js` applies pending migrations, `bun dist/public-browse-indexes.js` builds missing indexes concurrently, and `bun dist/public-browse-indexes.js --check` verifies all definitions and readiness without modifying them. The builder uses `CREATE INDEX CONCURRENTLY` outside a transaction, holds a dedicated session advisory lock, checks each existing index's complete definition and validity, and refuses an unexpected or invalid name. It never drops an index. Its lock timeout is two seconds and its statement timeout is 15 minutes. An interrupted build can leave an invalid index; inspect it before explicitly removing that invalid index concurrently and rerunning the builder.

## Staging qualification

1. Package the exact candidate, its migration set, and this builder as part of the repository-managed release. Inspect the actual release chain before selecting an orchestration point. The repository staging workflow currently dispatches to `linode-iac`; its checked-in deployment script restarts staging rather than doing a blue/green switch. Treat the installed host configuration as unverified until inspected. Any AWS infrastructure changes belong in `falsefloor/infra`; do not provision them manually. No new AWS resources are assumed for this database step. Confirm the target is the staging database and that its database role owns `games`, has `CREATE` on its schema, and may execute the lookup functions. Use staging-owned data or synthetic fixtures; do not copy production data or artifacts without the relevant approval.
2. Inspect the complete pending migration set before choosing the execution point: the packaged migrator applies **all** pending migrations, not only the browse functions. Confirm they are compatible with the current staging state and with the selected release procedure. Before applying anything, compare `bun dist/migrate.js --print-release-migration-set` from the exact candidate image with its approved release manifest. Run that image’s migrator, then builder, then `--check` against the same staging database before directing browsing traffic to this candidate. The builder and read-only checker exit nonzero on a missing, invalid, or differently defined index. The existing deployment workflow does **not** run or enforce these commands today; add and test its fail-closed orchestration before relying on this plan. The final `--check` uses a read-only snapshot and can run with a read-only database role; a successful build is not a substitute for the final check.
3. Measure database size and free disk, CPU/IO, WAL, active transactions, and game-write latency while each index builds. Check representative first-page, deep-page, status, game-type, and season filter plans against the actual staging dataset. `CONCURRENTLY` avoids a long write-blocking table lock but still waits for transactions, performs extra work, and can slow queries or writers through resource contention.
4. Verify the paged overview and both collections at desktop and mobile widths, search and clear transitions, cancellation, current visibility checks, and game continuity during the build. Record the exact artifact, migration set, indexes, timings, and measured load. Do not enable production from staging results without the user's separate production approval.

If a build fails or its session is interrupted, do not switch traffic to the candidate. If staging admission or the previous application was already stopped, the deployment workflow must restore the previous release and its normal admission state; that rollback is not implemented by these commands. Inspect the index state and definition, and decide the repair explicitly. A failed build may leave an invalid index that `IF NOT EXISTS` would not repair. After an approved repair, rerun the builder and verify all definitions. If an application release is rolled back, retain the additive indexes; rollback does not require dropping them. A rollback cannot claim write-load or storage recovery until that is separately measured.
