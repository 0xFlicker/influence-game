Grounding Context

The product thesis is an owner loop

Influence is positioned as persistent agent development plus spectating. The primary user first watches a personalized agent compete, then improves it; postgame edits and repeat participation are named product signals.

The format kernel already has breadth

Save-or-Eliminate, Vote Bomb, and Safety Bounce have canonical events, agent rules, Mingle context, simulation hooks, viewer choreography, and result presentation. The documented bar for more formats is distinct strategic behavior, not catalog size.

The improvement foundation is mature

Stable Agent Profiles, immutable Analytical Revisions, update receipts, waiting-seat propagation, roster freeze, owner reasoning access, and revision-separated season analysis exist. The missing product bridge is from one postgame insight to one deliberate edit and a visible next-revision learning state.

Analytics and consent are absent together

The web app has no general analytics SDK, consent preference store, or cookie banner. The privacy page mentions necessary cookies, analytics providers, and withdrawal, so optional browser tracking should arrive behind a runtime gate—not before it.

Useful metrics already exist server-side

Agents, joins, completions, eligible receipts, revisions, placements, and return participation can be derived from authoritative application data. Browser events are needed only for meaningful postgame inspection and viewer choices the server cannot see.

Privacy and authority boundaries are firm

Canonical events and projections remain the authority for game facts. Optional product telemetry must exclude prompts, reasoning, private dialogue, decision envelopes, provider payloads, and secrets; owner-private cognition can support a debrief without becoming analytics data.

Owner improvement loop

1. Owner Learning Loop v1

Description: After a completed game, surface one canonically grounded pivotal moment, invite the owner to record one intended behavioral change, deep-link into the relevant agent edit field, and issue a receipt for the resulting immutable revision. Show “current revision, awaiting evidence” beside “last measured revision,” then turn that state into a before/after view when eligible results arrive.

Illustrative loop: evidence becomes one owner decision, then a revision whose status stays visible until it has real results.

Axis
Owner improvement loop
Basis
direct: completed results, owner-authorized cognition links, agent edit forms, immutable revisions, and revision-separated season receipts already exist; the zero-game current-revision gap is explicitly documented.
Rationale
This completes the core watch → understand → improve → watch-again promise using foundations already built. It gives every edit a reason and every new revision a visible learning state.
Downsides
Selecting one defensible pivotal moment is non-trivial. The card must not auto-rewrite prompts, reveal foreign private data, or present one game as causal proof.

2
Product engagement analytics

2. Aha-Loop Ledger

Description: Measure the one journey that matters: completed game, meaningful postgame inspection, agent edit, and revised agent returned to play. Begin with authoritative server-derived agents, joins, completions, revisions, and receipts; add only the consent-gated browser events needed to observe postgame inspection.

Illustrative provenance split: application facts and optional browser observations stay visibly different even when they answer one product question.

Axis
Product engagement analytics
Basis
direct: strategy names completed watching, repeat participation, and postgame edits; server read models already contain most lifecycle facts; no general browser analytics provider exists.
Rationale
This tells the team whether the promised product loop happens and where it breaks before broad instrumentation or additional mechanics. Server-first measurement also creates value before consent-gated tracking is ready.
Downsides
“Meaningful inspection” needs a narrow product definition. The friends-and-owner audience is too small for overconfident statistical conclusions.

90%

3
Consent and data boundaries

3. Consent Firewall and Telemetry Customs Gate

Description: Build the requested real banner as an enforceable preference system: Necessary remains distinct from optional Analytics, Accept and Reject are equally usable, withdrawal is persistent and reachable, and optional code cannot initialize before permission. Put every allowed event and property behind a typed registry that rejects prompts, reasoning, private dialogue, provider payloads, secrets, and unregistered identifiers.

Illustrative enforcement: the preference screen controls runtime behavior, while the payload registry controls what may cross the analytics boundary.

Axis
Consent, preferences, and data boundaries
Basis
direct: the privacy policy mentions necessary cookies, analytics providers, and withdrawal; the root layout has no consent layer or analytics SDK; existing private-trace and spend boundaries already define prohibited payload classes.
Rationale
This safely unlocks the few browser observations the Aha-Loop Ledger needs. It also makes the banner a trust feature with enforceable behavior rather than a dismissible legal ornament.
Downsides
Purpose copy and jurisdictional behavior need counsel. Any analytics provider must honor the initialization gate rather than merely read a stored preference.

4
Format portfolio and watchability

4. Format Admission Gate

Description: Before a fourth format is built, require a short warrant naming an observed strategic or watchability failure, the canonical event signature expected to change, and a human watchability rubric for admission.

Illustrative gate: format work begins with a diagnosed deficiency and a predicted observable change.

Axis
Format portfolio and watchability
Basis
direct: the launch portfolio already has three anti-repeated formats, and the format plan defines validation as distinct coalition behavior rather than mere completion.
Rationale
This turns “more formats” into a falsifiable product decision and prevents mechanically different but strategically identical growth.
Downsides
The rubric needs consistent human review and enough comparable games. A strict gate can delay a mechanic that is plainly fun but hard to quantify.
Confidence
88%
Complexity
Low

Format portfolio and watchability

5. Format Film Room

Description: Generate short comparative cuts from existing games showing each format’s offer and choice, decisive social pivot, canonical reveal, and coalition consequence side by side. Use the cuts first as producer evidence, not as another public media product.

Axis
Format portfolio and watchability
Basis
direct: completed results, replay, House Highlights, turning points, canonical format events, and vote history already provide the source material for comparative cuts.
Rationale
A few comparable moments can show whether the formats create genuinely different stories or whether agent behavior and presentation are the real constraint.
Downsides
Media selection can become editorially subjective. Reusable extraction may be more work than a manual first review warrants.
